# omo-health

omo/senpi 세션을 옆에서 지켜보는 감시기입니다. 서브에이전트가 잘못된 도구 실행 때문에 멈추면 사람이 손대지 않아도 작업이 이어지게 합니다. 토큰 폭증, 캐시 폭풍, TPS 저하, 공급자 장애, 엉뚱한 곳 수정 같은 이상 징후는 제3자 입장에서 알려 줍니다.

감시기는 omo 설치 폴더 밖(`~/.omo-health`)에서 돌기 때문에 omo를 업데이트해도 지워지지 않습니다. omo 쪽에는 패키지(`~/.omo/agent/git/github.com/yjacket/omo-health`) 하나만 있습니다.

배경 사고: code-yeongyu/oh-my-openagent#8765 (호스트 도구 실행 후 서브에이전트 멈춤), #8762 (토큰 재발급 뒤 계정 차단). 설계 기록: `docs/design.md`(옛 설계, 현재 동작과 다름).

0.5.0에서 자가 치유 파이프라인(이슈·PR 자동 수정, 승인 요청, 규칙 제안)과 자동 업데이트·롤백을 없앴습니다. 경량·고급 판정기(`claude` CLI)도 분석가 하나로 바뀌었습니다.

## 설치와 제거

```powershell
omo install git:github.com/yjacket/omo-health
```

다음에 omo 세션이 시작되면 패키지의 센서가 나머지를 스스로 준비합니다. 1분 안에 다음이 갖춰집니다.
- 패키지의 현재 커밋을 고정 설치합니다. `git archive <sha>`를 `~/.omo-health/app/releases/<버전>-<짧은 sha>/`에 풀고 `app/current.json`에 `channel: "package"`, 버전, sha, 패키지 경로를 적습니다. 실제로 도는 코드는 이 고정 설치본이라, omo가 패키지 폴더를 갱신해도 실행 중인 감시기에 영향이 없습니다.
- 로그온할 때 자동 실행(`HKCU\...\Run\omo-health`, 창 없이 실행). 관리자 권한은 필요 없습니다.
- 감시기 시작. 세션을 여러 개 동시에 열어도 설치는 한 번만, 감시기는 하나만 뜹니다.

감시기는 WMI(`Win32_Process.Create`)로 띄웁니다. 그래서 감시기를 띄운 세션이나 Orca 터미널을 닫아도 감시기는 계속 돕니다. 그냥 detached로 띄우면 Orca가 터미널을 닫을 때 함께 종료됩니다.

감시기는 감시 대상과 같은 권한으로 뜹니다. 윈도우 무결성 수준이 낮은 감시기(로그온 자동 실행)는 관리자 권한 세션의 프로세스를 읽을 수도 끌 수도 없습니다. 관리자 권한으로 뜬 omo 호스트의 센서가 응답 중이면 감시기가 스스로 종료하고, 센서가 감시기를 그 권한으로 다시 띄웁니다. 재기동이 부적절한 권한으로 반복되지 않도록 30분에 한 번만 넘겨줍니다.

**업데이트:** `omo update --extensions`(또는 `omo update git:github.com/yjacket/omo-health`). 1분 안에 새 커밋이 고정 설치되고 감시기가 새 버전으로 바뀝니다. 열려 있는 세션은 쉬는 동안 새 센서로 다시 로드됩니다.

**제거:** omo 세션에서 `/health uninstall`(데이터까지 지우려면 `/health uninstall --purge`)을 입력한 다음 `omo remove git:github.com/yjacket/omo-health`를 실행합니다. 제거하면 자동 실행이 지워지고 감시기가 멈추며, 패키지가 남아 있어도 다시 설치하지 않습니다. 다시 켜려면 `/health install`을 입력합니다. `/health uninstall` 없이 `omo remove`만 했다면 감시기가 패키지가 사라진 것을 20분 뒤 알아채고 자동 실행을 지운 뒤 스스로 멈춥니다. 데이터(`~/.omo-health`)는 지우지 않습니다.

**예전 `install`에서 옮기기:** 저장소에서 `node bin/omo-health.mjs install`로 설치했다면 `omo install git:github.com/yjacket/omo-health`만 실행하면 됩니다. 패키지 센서가 고정 설치를 넘겨받고 예전 센서 스텁(`~/.omo/agent/extensions/omo-health-sensor.ts`)을 지운 뒤, 열려 있는 세션을 쉬는 동안 다시 로드합니다. 옮기는 동안 센서가 두 번 로드되지 않습니다.

**개발용:** 저장소를 직접 쓰려면 지금처럼 `node bin/omo-health.mjs install`(HEAD 고정 설치, 커밋하지 않은 변경이 있으면 거부) 또는 `install --dev`(이 폴더를 그대로 실행)를 씁니다. `--dev`로 설치한 동안에는 패키지가 설치를 넘겨받지 않습니다. 저장소에서 제거할 때는 아래 명령을 씁니다.

```powershell
node C:\dev\omo\omo-health\bin\omo-health.mjs uninstall          # 스텁·자동 실행 제거, 감시기 중지
node C:\dev\omo\omo-health\bin\omo-health.mjs uninstall --purge  # ~/.omo-health 데이터까지 삭제
```

## 멈추고 끄는 법

```powershell
node C:\dev\omo\omo-health\bin\omo-health.mjs pause --minutes 30  # 자동 조치만 30분 멈춤 (감지·알림은 계속)
node C:\dev\omo\omo-health\bin\omo-health.mjs resume
node C:\dev\omo\omo-health\bin\omo-health.mjs stop               # 감시기 중지 (센서가 다시 띄우지 않음)
node C:\dev\omo\omo-health\bin\omo-health.mjs start
```

대시보드(`/health ui`)에서도 일시정지·재개와 주요 기능 켜고 끄기를 할 수 있습니다. 아래 "대시보드"를 보세요.

`~/.omo-health/config.json`에서 설정을 바꿀 수 있습니다. 감시기는 바뀐 파일을 재시작 없이 다음 확인(약 15초 안)에 반영합니다.
- `{"mode": "shadow"}`: 조치 대신 "했을 조치"만 기록합니다.
- `{"actions": {"kill": false}}`: 조치 종류별로 끕니다. 종류는 `kill`, `detach`, `release`, `relay`, `wake`, `nudge`, `revert`, `abortHungTurn`, `toast`, `resume`입니다. `resume`을 끄면 크래시한 세션을 새 탭에서 다시 열지 않고 알림만 띄웁니다.

## 명령

| 명령 | 하는 일 |
| --- | --- |
| `daemon` | 감시기를 이 창에서 실행 (`--shadow`, `--config <파일>`, `--echo`) |
| `start` | 감시기를 백그라운드로 실행 |
| `stop` | 감시기를 멈추고 계속 멈춰 있게 함 |
| `status` | 감시기, 세션, 최근 사건 보기. `~/.omo-keepwarm/status/_global.json`이 있으면 keepwarm 상태 줄도 보여줌 (`--json`: 에이전트용, `keepwarm` 필드) |
| `pause` | 자동 조치 일시 정지 (`--minutes N`) |
| `resume` | 자동 조치 재개 |
| `ui` | 로컬 대시보드를 기본 브라우저로 열고 바로 끝남 (`--no-open`, `--json`, `--idle-minutes N`). 서버는 30분 동안 쓰지 않으면 스스로 닫힘 |
| `diagnose` | 서브에이전트를 취소하기 전에 진단: 무엇을 기다리는지(도구 호출·명령·경과 시간), 마지막 진척, CPU와 자식 프로세스, 판정(진행 중·멈춤·반복·쉬는 중)과 권고(기다리기·셸만 풀기·취소). 모델을 부르지 않음 (`<작업 id 또는 세션 id> [--json]`) |
| `report` | 서브에이전트나 세션의 문제를 omo-health에 보고 (`<작업 id 또는 세션 id> <내용> [--json]`). 같은 보고는 1시간에 한 번, 전체는 시간당 10건까지 기록 |
| `install` | HEAD 고정 설치(`--dev`: 이 폴더를 그대로 실행, `--from-package`: 패키지 설치. 보통은 센서가 실행), 스텁, 로그온 자동 실행, 감시기 시작 |
| `uninstall` | 스텁·자동 실행 제거, 감시기 중지 (`--purge`) |
| `doctor` | 필요한 것이 모두 갖춰졌는지 표로 점검 |
| `scan` | 지난 로그·세션을 탐지기에 재생 (`--from ISO --to ISO [--json]`) |
| `replay` | 픽스처 폴더를 가짜 시계로 엔진에 재생 (`<폴더> [--json]`) |

설치 뒤에는 저장소 위치와 상관없는 안정된 경로로 같은 명령을 쓸 수 있습니다. 부트스트랩이 `current.json`이 가리키는 설치본을 실행합니다.

```powershell
node %USERPROFILE%/.omo-health/app/boot.mjs <command>
```

PowerShell에서는 `%USERPROFILE%` 자리에 `$env:USERPROFILE`을 씁니다.

omo 세션 안에서는 하단 상태줄에 `헬스 ✓` 또는 경고가 보입니다. 하단 상태줄에는 서브에이전트 문제만 올라옵니다. 멈춤, 무응답, 죽거나 오류로 끝난 서브에이전트, 폭주, 반복 루프, 그리고 사람만 고칠 수 있는 문제(로그인 만료, 계정 차단 등)입니다. 토큰 급증(D4), 설정 리로드(D11), 감시기 자체 점검(D12), 작업 폴더 밖 수정(D14), 범위 점검(D15)은 `/health`와 `status --json`에서만 보입니다. 전부 하단에 보려면 `config.json`에 `"footer": { "showAll": true }`를 넣습니다. `/health`를 입력하면 최근 24시간 사건과 보고서 경로가 나타나고, 다시 입력하면 닫힙니다. 같은 화면에 그 세션의 원래 목표도 나옵니다. 세션이 살아 있는 작업을 기다리며 쉬고 있으면 하단에 `👀 DAG3/5`(워크플로 완료 노드/전체) 또는 `👀 대기2`(살아 있는 작업 소스 수)가 보이고, 대시보드 세션 현황에는 `작업 대기`로 나옵니다. 사용자에게 묻는 도구(ask-user)를 기다리면 세션 현황에 `사용자 대기`, 작업이 아닌 대기만 있으면 그냥 `대기`로 나오고, 이 두 경우 하단 상태줄에는 대기 표시가 붙지 않습니다. D16, D17, D22는 하단에 올리지 않습니다. `/health ui`는 대시보드를 엽니다. `/health report [작업 id] <내용>`은 이 세션(또는 그 작업)의 문제를 omo-health에 보고합니다. 아래 "종료 전 진단과 문제 보고"를 보세요.

## 대시보드

감시기가 무엇을 했는지 한 화면에서 보고, 필요하면 그 자리에서 제어하는 로컬 페이지입니다. 필요할 때만 뜨고, 먼저 알리지 않습니다.

여는 법:
- omo 세션에서 `/health`를 입력합니다(`/health ui`도 같음). 예전 요약은 `/health widget`으로 봅니다.
- 새 버전을 설치하면 이미 열려 있던 세션도 쉬는 동안 확장을 다시 불러 새 감시기로 바뀝니다(설치본 하나당 최대 3번, 10분 간격으로 요청).
- 터미널에서 `node %USERPROFILE%/.omo-health/app/boot.mjs ui`를 실행합니다(저장소에서는 `node bin/omo-health.mjs ui`).

명령은 주소를 출력하고 기본 브라우저를 연 뒤 바로 끝납니다. 서버는 뒤에서 따로 돌다가 30분 동안 요청이 없으면 스스로 닫힙니다. 페이지의 자동 새로 고침은 요청으로 세지 않으므로, 잊힌 탭이 서버를 붙잡지 않습니다. 브라우저가 안 열리면 출력된 주소를 직접 엽니다. `/health ui`는 브라우저가 열렸으면 주소(토큰 포함)를 화면에 남기지 않고 포트만 알려 주며, 안 열렸을 때만 주소를 보여 줍니다. `OMO_HEALTH_HOME`, `OMO_HEALTH_OMO_HOME`, `OMO_HEALTH_CLAUDE_HOME`(테스트·샌드박스용) 중 하나라도 있으면 브라우저를 열지 않고 주소만 출력합니다. `OMO_HEALTH_CONFIG`만 있을 때는 열립니다. `--no-open`은 브라우저를 열지 않고, `--json`은 주소와 브라우저를 열었는지(`opened`)를 한 줄 JSON으로 출력하며, `--idle-minutes N`은 유휴 종료 시간을 바꿉니다. 대시보드를 연 omo 세션이나 터미널을 닫으면 서버도 함께 닫힐 수 있습니다.

탭은 세 개입니다.
- 세션 현황: 지금 돌고 있는 세션과 서브에이전트, 각자의 상태와 열린 문제.
- 세션 기록: 끝난 세션의 기록(`sessions/ended-*.jsonl`).
- 관리: 아래 항목과 제어.

관리 탭에 보이는 것:
- 지금: 감시기 상태(실행 중, 응답 없음, 비정상 종료, 중지됨, 꺼짐), 일시정지, 모드, 세션·서브에이전트 수, 사람이 확인할 일, 열린 문제.
- 작업 진단: 돌고 있는 서브에이전트나 세션을 골라 `diagnose`와 같은 진단(판정, 권고, 기다리는 호출, 프로세스, 감시기 조치)을 봅니다. 목록은 페이지를 열 때 읽고, 진단은 누를 때만 몇 초 동안 프로세스를 살펴봅니다.
- 조사 목록: 최근 조사(아래 "조사 목록과 분석가")의 대상, 계기, 상태, 분석가 판정과 조치.
- 최근 7일: 같은 종류를 한 줄로 묶어 개수와 일별 분포를 보여 주고, 펼치면 최근 예시 5건이 나옵니다. 조치는 결과별로 세고, 설정 변경도 보입니다.
- 설정: 아래 스위치 9개의 파일 값과 감시기 적용값, 기본값과 다른 값, 설정 경고.

제어: 일시정지(15분, 1시간, 재개할 때까지)와 재개, 그리고 아래 스위치입니다. 모두 CLI와 같은 파일(`pause`, `config.json`)을 씁니다. 스위치를 기본값으로 돌리면 `config.json`에서 그 키를 지우고, 다른 키는 건드리지 않습니다.

| 스위치 | 뜻 |
| --- | --- |
| `mode` | `auto`는 조치를 실행하고, `shadow`는 조치하지 않고 "했을 조치"만 기록 |
| `actions.kill` | 멈춘 도구 호출의 원인 프로세스와 주인 없는 monitor 감시 프로세스를 종료 |
| `actions.detach` | 포그라운드 서버는 두고 그 서버를 기다리던 셸만 종료 |
| `actions.release` | 끝나지 않는 대기나 입력 대기에 걸린 셸 트리를 종료 |
| `monitorOrphans.enabled` | 주인 없는 monitor 감시 프로세스를 60초 유예 뒤 정리 (`actions.kill`도 켜져 있어야 함) |
| `config.autoRevert` | 설정을 바꾼 직후 공급자 오류가 이어지면 `settings.json`을 직전 정상본으로 되돌림 |
| `align.enabled` | 원래 요청에서 멀어진 세션에 범위를 다시 확인하라는 짧은 메시지 |
| `analyst.enabled` | 멈춤 의심과 이상 신호를 분석가에게 물음. 끄면 멈춤 의심은 조사 목록에 남기만 하고 풀리지 않음 |
| `footer.showAll` | 하단 상태줄에 모든 문제 표시 (끄면 서브에이전트 문제와 사람만 고칠 수 있는 문제만) |

반영 시점:
- 감시기는 매 확인(기본 15초) 전에 `config.json`의 수정 시각과 크기를 봅니다. 바뀌었으면 재시작 없이 새 값을 반영하고, 설정 구역에 "감시기에 반영됨"이 보입니다.
- `sessions.tailBytes`는 새로 추적하는 세션부터 적용됩니다.
- 감시기가 꺼져 있으면 다음 시작 때 반영됩니다.
- 실행 중에 `config.json`을 읽을 수 없으면(저장 도중인 파일 등) 직전 설정을 유지합니다. 다시 시작할 때 읽을 수 없으면 마지막 정상 사본 `config.last-good.json`을 씁니다. 반영과 거부는 결정 로그에 남습니다.
- `--shadow`로 실행한 감시기는 `mode`를 바꿔도 기록만 합니다.

보안:
- 서버는 `127.0.0.1`에만 열리고 포트는 운영체제가 고릅니다. 다른 컴퓨터에서는 접속할 수 없습니다.
- 실행할 때마다 새 토큰을 만들고 디스크에 쓰지 않습니다. 토큰은 주소의 `#` 뒤에 있고, 페이지가 읽은 뒤 주소에서 지웁니다.
- 다른 웹사이트가 이 서버를 읽거나 조작하지 못하도록 Host와 Origin을 검사하고, CORS를 허용하지 않으며, 정해진 키와 값만 받습니다.
- 프로세스를 종료할 권한이 있는 감시기는 네트워크 포트를 열지 않습니다. 서버는 별도 프로세스입니다.

하지 않는 일: 알림, 배지, 하단 상태줄 문구로 이 페이지를 가리키지 않습니다. 감시기 종료·재시작 버튼, 임계값 편집기, 원시 설정 편집기는 없습니다.

## 종료 전 진단과 문제 보고

서브에이전트가 오래 돈다고 바로 취소하면 거의 끝난 작업을 버리게 되고, transcript를 읽어 점검하면 토큰이 많이 듭니다. `diagnose`는 모델 없이 몇 초 만에 답합니다.

```powershell
node %USERPROFILE%/.omo-health/app/boot.mjs diagnose st_01a0ed19          # 사람용 한국어
node %USERPROFILE%/.omo-health/app/boot.mjs diagnose st_01a0ed19 --json   # 에이전트용
```

- 대상: 작업 id(`st_...`), 세션 id, 또는 세션 id 앞 8자 이상. 못 찾으면 진단할 수 있는 작업과 세션을 보여 주고 1로 끝납니다.
- 보여 주는 것: 기다리는 도구 호출(도구, 명령, 경과 시간, D1 분류와 규칙), 그 호출의 프로세스(CPU, 메모리), 출력 파일의 크기와 마지막 변경, 마지막 진척 시각(대화 기록이나 출력 파일), 반복 루프(D10), 돌고 있는 자식 서브에이전트, 감시기의 다음 조치와 그 시각, 최근 24시간 감시기 조치.
- 판정과 권고:
  - `진행 중`: 기다리면 됩니다(제한 시간이 있는 명령, CPU나 쓰기가 있는 작업, 아직 이른 호출, 자식 서브에이전트 대기). 원인을 알 수 없는 호출(R11)은 트리가 완전히 조용하지 않으면 `기다리세요 (판정 대기)`입니다. 감시기가 분석가에게 묻고 멈춤 판정이 나올 때만 셸을 풀기 때문입니다. 분석가가 꺼져 있으면 감시기는 이 호출을 풀지 않습니다.
  - `멈춤`: 셸 트리만 끝내면 호출이 결과를 돌려받는 경우(끝나지 않는 대기, 입력 대기, 포그라운드 서버, CPU만 쓰는 읽기 명령, 메모리 폭주, CPU도 쓰기도 없이 10분 넘게 조용한 호출, 서브에이전트 호출이 대화 기록도 출력도 없이 15분 조용한 R12 조용한 멈춤)는 `셸만 풀어 주세요`와 풀 대상 프로세스를, 풀 셸이 없거나 호스트가 사라진 경우는 `취소하세요`를 권합니다.
  - CPU와 출력을 짧은 표본으로 보는 판정(R11, R12)은 추정이라고 이유에 적고 JSON에 `heuristic: true`를 넣습니다. 짧은 표본으로는 쓰기 사이에 잠시 쉬는 트리와 헛도는 트리를 구별할 수 없으므로, CPU를 쓰는 트리는 조용한 멈춤으로 보지 않습니다.
  - `반복`: 같은 호출이나 같은 오류를 되풀이합니다(취소). 재시작 폭주는 셸만 풀면 됩니다.
  - `쉬는 중`: 작업이 끝났거나 세션이 입력을 기다립니다.
- 근거: 감시기와 같은 수집기(세션 기록, 작업 저장소, 센서 하트비트)와 같은 D1 규칙 분류기로 지금 새로 모읍니다. 프로세스는 3초 간격으로 두 번 찍어 CPU를 봅니다. 감시기 상태 파일(`status/`)은 읽지 않습니다. 그 파일은 감시기가 돌 때만 최신이고, 감시기가 꺼져 있으면 지난 일을 말하며, 프로세스 트리나 CPU 표본을 담고 있지 않기 때문입니다. 그래서 감시기가 꺼져 있어도 결과가 맞습니다. 감시기가 돌고 있으면 예정된 자동 조치와 그 시각을 함께 알려 줍니다.

`omo-health report <작업 또는 세션 id> <내용>`(에이전트)과 `/health report [작업 id] <내용>`(운영자, 작업 id가 없으면 이 세션)은 문제를 omo-health에 알립니다. 도구로 등록하지 않으므로 어떤 세션의 프롬프트 토큰도 늘지 않습니다. 멈춘 에이전트는 스스로 보고하지 못하므로 보고는 감지를 보완하는 신호입니다.
- 보고는 `~/.omo-health/intake/`에 쌓이고, 감시기가 다음 확인(약 15초 안)에 사건으로 기록하고 증거 스냅샷을 남깁니다. 사건 파일은 감시기만 씁니다. 감시기가 꺼져 있으면 다음 시작 때 기록합니다.
- 보고와 감지는 서명으로 합쳐집니다. 대상(그 세션, 그 작업, 이름을 댄 세션의 서브에이전트)에 지금 감지가 있으면 그 감지가 기록하는 사건(예: `upstream/D1/stall/inproc`)에 합쳐지고, 그런 사건이 없는 감지면 `report/<탐지기>/<종류>/<분류>`, 아무것도 감지되지 않았으면 `report/undetected`에 모입니다. 서명은 대상이 아니라 문제를 가리키므로 같은 문제를 여러 번 보고해도 사건과 이슈는 하나입니다.
- 기록된 보고는 조사 목록에 `trigger: report`로 올라가고 분석가가 봅니다. 결과(판정, 진단, 조언)는 대상을 가진 세션에 갑니다. 서브에이전트에 대한 보고는 부모 세션에 서브에이전트에게 전달할 영어 문장과 함께, 메인 세션에 대한 보고는 그 세션의 다음 턴 알림으로 갑니다. 분석가를 쓸 수 없거나 보고 한도(하루 3회, `analyst.reports.perDay`)를 다 썼으면 증거 스냅샷의 규칙 진단을 보냅니다. 보고 한도는 멈춤 조사의 한도와 따로 셉니다. 보고는 프로세스 조치를 일으키지 않습니다(분석가 선택지에 종료가 없음). 보고 내용은 모델에 데이터로만 전달되고, 토큰은 결정 로그와 같은 방식으로 가립니다.
- 같은 대상에 같은 내용(대소문자·공백 무시)은 1시간에 한 번만, 전체는 시간당 10건까지 기록합니다. 넘는 보고는 기록하지 않고 `intake/processed/`에 결과(`duplicate`, `rate-limited`)만 남깁니다. CLI는 접수와 중복이면 0, 한도 초과면 1로 끝납니다.

증거 스냅샷: 보고가 오거나 서브에이전트 작업을 멈출 수 있는 감지(D1, D2, D5, D8, D10, D17)가 열리면 감시기가 그 순간 `~/.omo-health/snapshots/<ms>-<이유>-<대상>.json`을 씁니다. 진단 결과, 호스트의 프로세스 계보(조상, 호스트, 그 아래 전부와 각 프로세스가 어느 도구 호출의 것인지), 소유 세션의 최근 대화 30개(도구 출력 본문 제외), 세션 기록과 출력 파일의 크기가 들어 있고, 1분 동안 매 확인마다 크기를 다시 재서 아직 자라는지 보여 줍니다. 같은 감지는 10분에 한 번만 찍고, 7일이 지나거나 200개를 넘으면 오래된 것부터 지웁니다. 모델은 부르지 않습니다.

전역 AGENTS.md에 이 한 줄을 넣기를 권합니다(운영자 파일이라 omo-health가 고치지 않습니다). `omo-health`가 PATH에 없으면 `node %USERPROFILE%/.omo-health/app/boot.mjs`로 바꿉니다.

> Before cancelling a long-running subagent, run `omo-health diagnose <task>` and report it.

## 자동으로 하는 일 (기본값)

서브에이전트의 도구 호출이 끝나지 않을 때, 무엇을 기다리는지 분류한 뒤 원인 프로세스만 정확히 처리합니다.

| 분류 | 판단 근거 | 조치 시점 | 조치 |
| --- | --- | --- | --- |
| 메모리 폭주 | 5분간 분당 100MB 이상 증가, 4GB 이상, 또는 커밋 90% 이상이면서 가장 큰 omo 도구 트리 | 즉시 (스냅샷 2회 이상) | 해당 프로세스만 종료 |
| 포그라운드 서버 | LISTEN 포트, 로그의 listening 문구, 백그라운드 의도 | 2분 | 기다리던 셸만 종료, 서버는 유지 |
| 입력 대기 | CPU 0 + 대화형 프로그램(less, vim, ssh 등) | 3분 | 셸 트리 종료 |
| 읽기 명령 폭주 | grep/rg/find/yes 등이 CPU만 쓰며 진척 없음 | 10분 | 폭주 프로세스만 종료 |
| 재시작 폭주 | 트리가 같은 프로그램을 스냅샷마다 새로 띄우고 거의 전부 즉시 죽음 (D17) | 재실행 관측 1분 후 | 셸 트리 종료 |
| 끝나지 않는 대기 | `tail -f`, 1시간 이상 sleep, 한도 없는 until/while 루프 | 15분 | 셸 트리 종료 |
| 원인 불명 | 위 어디에도 해당 없음 | 10분(`stall.unknownJudgeMs`)에 조사 목록에 올리고 분석가에게 물음 | 분석가가 멈춤(`stuck`)이라 하면 셸 트리 종료. 시간이 지났다는 이유만으로는 풀지 않음 |
| 조용한 멈춤 (서브에이전트만) | 제한 시간 있음·진행 중·원인 불명이라도 15분(`stall.quietMs`) 동안 기록(transcript) 이벤트도 출력도 없음. 출력은 리디렉션한 파일이 커지거나, 트리가 CPU를 쓰면서 쓰기를 한 것만 칩니다 | 15분에 조사 목록에 올리고 분석가에게 물음 | 분석가가 멈춤이라 하면 셸 트리 종료 |
| 제한 시간 있음 / 진행 중 | `timeout N`, 인자 timeout, 빌드·테스트·설치, 파일 쓰기 증가 | 진행 중이 60분(`stall.progressingMaxMs`)을 넘으면 조사 목록에 올리고 분석가에게 물음 | 분석가 판정에 따름 |

메모리 폭주부터 끝나지 않는 대기까지는 구체적 증거가 있는 규칙(R5, R5b, R6, R7, R8, R9)이라 분석가 없이 조치합니다. 원인 불명, 조용한 멈춤, 오래 진행 중인 호출은 멈춤 의심일 뿐이라, 분석가 판정이 없으면 풀지 않습니다.

조치한 뒤에는 90초 안에 도구 결과가 도착하는지 확인합니다. 결과가 없으면 한 단계씩 올립니다: 폭주 프로세스 종료 → 셸 트리 종료 → 부모 세션에 `task_cancel` 권고.

서브에이전트에 대한 프로세스 조치는 조용합니다(`quiet`). 조사 목록과 결정 로그에만 남고 부모 세션에는 보내지 않습니다. 부모 세션은 `relay-cancel` 메시지 하나만 받습니다. 분석가가 회복 불가(`unrecoverable`)라 했을 때, 같은 작업이 30분(`analyst.repeatWindowMs`) 안에 다시 멈춤 판정을 받았을 때, 또는 단계를 끝까지 올려도 호출이 풀리지 않았을 때입니다. 메시지에는 서브에이전트에게 그대로 전달할 영어 문장이 들어 있습니다. 한 번 멈춰 조치나 알림을 받은 작업은 1시간(`stall.restallWindowMs`) 동안 더 가까이 봅니다. 그 작업의 다음 호출은 조용한 멈춤과 첫 재판정을 15분·10분 대신 5분(`stall.restallMs`)에 합니다.

그 밖에 자동으로 하는 일은 다음과 같습니다.
- 에이전트가 백그라운드로 띄운 작업이 같은 프로그램을 수분간 무한 재실행(크래시/재시도 루프)하면(D17, 0.8.0부터 실제로 동작함), 3분(`respawn.killAfterMs`) 넘게 지속될 때 먼저 분석가에게 묻습니다. 멈춤이라 하면 다시 띄우는 프로세스만 종료하고 소유 세션에 알립니다. 진행 중이라 하면 다음 판정까지 기다리고, 확인을 요청하면 소유자에게 한 번 알립니다. 어떤 답이든, 분석가가 답하지 못해도, 처음 발견하고 30분(`respawn.maxHoldMs`)이 지나면 종료합니다. 재실행 주체가 메인 세션이면 알리기만 합니다. `respawn.enabled`를 끄면 이 감지와 호출 단위 `respawn-loop` 분류가 함께 멈춥니다.
- 서브에이전트 도구 호출의 프로세스 트리가 이 PC의 평소 값보다 훨씬 많이 프로세스를 띄우거나, CPU를 쓰거나, 메모리나 쓰기가 늘면(기준선 이탈) 그 값을 멈춤 감지의 증거에 붙이고 결정 로그에 `baseline-deviation`을 남깁니다. 평소 값은 1분마다 재서 기록 DB(`omo-health.db`)에 최근 7일을 남기고, 99.5% 분위수와 robust z(6 이상)로 비교합니다. 이탈은 스스로 아무 조치도 하지 않습니다.
- `tool.monitor` 명령 감시가 끝났거나 그 세션이 꺼졌는데 남은 감시 프로세스를 60초 유예 후 조용히 정리합니다(D16). 판단은 프로세스로만 합니다(실행 셸이 사라졌거나 그 부모인 senpi 호스트가 사라짐). 소유 세션에는 다음 턴에 알림을 한 번 붙입니다(턴을 새로 시작하지 않음). 알림에는 UTC와 KST 시각이 있고, persistent monitor는 senpi가 재시작 때 스스로 다시 실행하므로 다시 등록하지 말라고, 나머지는 필요하면 다시 등록하라고 적습니다. 전달되지 못한 알림은 30분이 지나거나(`withdrawn:expired`), 알림에 적힌 감시가 모두 다른 실행 셸 아래 다시 돌고 있으면(senpi가 복원함, `withdrawn:restored`) 거둬들이고 결정 로그에 남깁니다.
- 메모리 reflection 실행(D22)이 `final.json`으로 끝났는데 남은 `node`/`bun` 자식 프로세스는 10분 유예 후 조용히 정리합니다. 최근에 생긴 같은 실행 디렉터리의 프로세스는 건드리지 않고, 종료 직전에 pid·생성시각·명령을 다시 확인합니다. 알림은 없고 결정 로그에만 남습니다.
- omo 호스트가 정상 종료 없이 죽으면(Bun 크래시 등) 기록합니다(D18). 센서 하트비트 파일이 죽은 pid로 남아 있고, 그 하트비트가 호스트와 함께 멈췄다는 증거(감시기가 직전까지 살아 있는 호스트를 봤거나, senpi의 `process-crashes` 생존 표식·크래시 기록 시각이 맞음)가 있어야 크래시로 봅니다. 진행 중인 턴이나 활성 목표(ulw 루프 포함)가 있었으면 같은 herdr 작업공간에 새 탭을 열고 그 탭의 새 셸에서만 `omo --session <세션 id>`를 실행합니다. 원래 pane에는 아무것도 입력하지 않고 진단용으로 그대로 둡니다. 원래 pane이 남아 있고, 셸 프롬프트에 멈춰 있고(포그라운드 프로그램 없음), 작업 폴더가 같을 때만 새 탭을 엽니다. 새 센서가 뜨면 "이전 실행이 크래시로 끊겼고 프로세스 안 서브에이전트는 사라졌으니 작업 트리를 확인하고 이어 가라"는 안내를 한 번 보냅니다. 턴은 새로 시작하지 않습니다(유휴면 `nextTurn`, 이미 목표로 다시 돌고 있으면 `steer`). 진행 중인 턴도 활성 목표도 없던 크래시는 열린 할 일이나 서브에이전트가 남아 있어도 기록만 합니다(목표를 이미 달성한 세션이 종료 중에 죽는 경우). 크래시 뒤 같은 작업 폴더에서 다른 세션이 돌고 있거나 더 늦게 기록된 세션 파일이 있으면 누군가 이어받은 것으로 보고 기록만 합니다. 세션당 시간당 2번(`crashResume.perHour`)까지만 재개하고, 30분 안에 2번 크래시하거나(`crashResume.loopCount`, `crashResume.loopWindowMs`), 새 탭을 열 수 없거나(herdr 밖, pane이 닫히거나 다른 프로그램 실행 중), 3분 안에 새 센서가 뜨지 않으면(`crashResume.startupMs`) 재개를 멈추고 세션과 작업 폴더를 적은 윈도우 알림을 한 번 띄웁니다. 결과를 기록한 뒤 남은 하트비트 파일은 지웁니다. 마지막 하트비트로부터 10분(`crashResume.maxAgeMs`)이 지나서야 처음 발견한 남은 하트비트(설치 직후 쌓여 있던 것 등)는 재개하지 않고 한꺼번에 조용히 정리합니다.
- omo-limitless가 사용량 한도로 세션을 내리며 남긴 파킹 기록(`~/.omo-health/parks/<세션>.<생성 ms>.park.json`)을 한도 리셋 1분 뒤에 이어받아(D20 `park-resume`, `actions.resume` 스위치) 원래 터미널 앱(Orca면 `orca terminal create`, herdr면 D18과 같은 새 탭)에서 `omo --session <세션 id>`를 다시 띄웁니다. 기록은 `pending` → `claimed` → `launched` → `completed`로 바뀌고 처음 쓴 뒤로는 omo-health만 고칩니다. 완료는 재개된 세션의 확인 파일(`.ack.json`)이나 살아 있는 센서 하트비트로만 판정합니다. `--session <세션 id>` 프로세스가 떠 있으면 시작 중으로 보고 기다리고, 15분 넘게 확인이 없으면 `failed: hung-start`로 한 번 알리며 그 프로세스는 건드리지 않습니다. 청구 뒤 2분, 실행 뒤 5분이 지나도록 확인·하트비트·프로세스가 없으면 다시 `pending`으로 돌리고, 그 전에 omo-health가 열었던 터미널이 빈 채 남아 있으면 그것만 닫습니다. 3번 시도해도 안 되면 `failed: relaunch-exhausted`로 한 번 알립니다. D18과 같은 세션당 시간당 한도(`crashResume.perHour`)에 걸리면 `pending`(`lastError: rate-capped`)으로 기다리며 시도 횟수에 넣지 않습니다. 한 세션에 끝나지 않은 기록이 여러 개면 가장 새 것만 띄우고 나머지는 `superseded`로 둡니다. 터미널을 모르는 기록(`unknown`)은 `failed: no-launcher`로 한 번 알리고, omo-limitless가 직접 띄우는 기록(`self`)은 정리만 합니다. 끝나지 않은 기록이 있는 동안 데몬은 유휴 종료하지 않고 D18은 그 세션을 재개하지 않습니다. 끝난 기록과 확인 파일은 7일 뒤 지웁니다. 데몬은 매 틱 `~/.omo-health/daemon.json`에 `capabilities: ["park-resume"]`를 실어 보내고, omo-limitless는 이 표식이 있을 때만 세션을 내리며 맡길 수 있는 데몬 없는 파킹이 남지 않게 합니다.
- 활성 목표가 있는 메인 세션이 깨어날 거리 없이 멈춰 있으면 그 세션을 깨웁니다(D21 `goal-liveness`, `src/detect/goal-liveness.mjs`). 센서 하트비트의 `wakeSources`(소스별 개수, `terminal-monitors` 포함), `holds`, `goalWait`(목표 이어가기 타이머)를 봅니다. 세션이 유휴인데 남은 깨움 소스가 실제로는 끝났거나, omo-keepalive가 백스톱을 붙잡은 채 세션이 오래 조용하면 사유와 함께 감지합니다. 기본 사유는 네 가지입니다(0.8.0에서 더해진 근거 사유 네 가지는 아래에 따로 적습니다): `leaked-monitor`(끝난 monitor가 소스로 남음), `leaked-task`(끝난 서브에이전트 작업이 남음), `leaked-workflow`(끝난 워크플로가 남음), `silent`(`omo-keepalive` 보류 중인데 세션 이벤트가 없음). 작업과 워크플로 기록은 senpi가 실제로 쓰는 곳(작업 폴더의 `.omo/senpi-task`에 기록이 있으면 그곳, 없으면 `~/.omo/agent/projects/<폴더 이름>-<해시>/senpi-task`)에서 읽고, 그곳이 없거나 기록 하나라도 읽지 못하면 새었다고 보지 않습니다. 끝난 소스는 그 상태가 `graceMs`(120000, 2분) 이어지면 깨우고, `silent`는 마지막 이벤트에서 `livenessMs`(3570000, 약 59.5분)가 지나면 깨웁니다. 깨움은 그 세션 자신의 inbox로 가고(`wake`, `followUp`, 턴 시작, 5분 뒤 만료), 같은 세션은 `minWakeGapMs`(3570000) 안에 다시 깨우지 않습니다. `actions.wake` 스위치를 따르며 프로세스 조치는 하지 않습니다. 이 감지가 켜져 있으면 데몬은 `daemon.json`의 `capabilities`에 `"goal-liveness"`를 싣고, `goalLiveness: { wakeReady, actionScope }`를 매 틱 다시 씁니다. `wakeReady`는 지금 모드, 일시정지, 스위치에서 목표 깨움이 실제로 실행되는지를 뜻하고, `actionScope`는 `config.actionScope`(비었으면 `null`)입니다. omo-keepalive의 백스톱은 이 표식과 그 세션의 새 하트비트(`goalLivenessSchema: 1`)가 모두 있을 때만 senpi의 목표 백스톱 타이머를 붙잡아 둡니다(`omo-keepalive` 보류). omo-health가 세션을 지켜보고 있을 때만 타이머를 미루는 셈입니다. 센서 쪽 변경은 이미 열린 세션에는 그 세션을 다시 시작해야 반영됩니다(`/reload`로는 바뀌지 않습니다). 끄려면 대시보드의 "목표 대기 확인" 스위치를 끄거나 `{"goalLiveness": {"enabled": false}}`로 설정합니다. 그러면 표식이 빠지고 keepalive도 보류하지 않습니다. 0.8.0부터는 세션의 살아 있는 작업(서브에이전트 작업, 워크플로 실행, eval 로그)도 읽습니다. 노드의 작업은 이미 끝났는데 실행에 반영되지 않은 워크플로(`unfolded-workflow`)나 실행할 노드가 하나도 없는 워크플로(`stalled-workflow`)는 2분(`goalLiveness.foldGraceMs`) 뒤 실행, 노드, 작업 id를 적어 깨웁니다. 명령 monitor나 백그라운드 세션의 프로세스 트리 전체가 30분(`goalLiveness.quietMs`) 동안 아무 일도 하지 않으면(`idle-monitor`, `idle-background`, 종류 `goal-wait-idle`) 먼저 분석가에게 묻고, 정상이라 하면 미루며, 늦어도 10분(`goalLiveness.idleWakeHoldMs`) 뒤 깨웁니다. 상시 감시로 띄운 monitor(persistent)는 원래 조용한 것이 정상이라 유휴로 보지 않고 한 시간 기준의 `silent` 확인만 받습니다. 끝난 소스로 깨울 때는 그 작업, 워크플로 실행, monitor와 그 프로세스를 적어 보내고, 작업 기록을 읽지 못하면 진행했다고 보지 않아 예전처럼 한 시간 기준으로 깨웁니다. `silent`는 선언된 작업 소스가 `quietMs` 안에 진척을 보였으면 미룹니다. 사람만 기다리는 대기(ask-user)는 예전처럼 한 시간마다 깨웁니다. 깨움 메시지에는 대기의 근거(실행, 노드, 작업, 프로세스, 멈춘 분)와 분석가의 원리·회피가 들어갑니다.
- 감시기가 10분(`bootGap.minGapMs`) 넘게 꺼져 있었으면(재부팅, D18이 이어 줄 수 없는 긴 중단) 그 기록을 `~/.omo-health/boot-gaps/`에 남깁니다. 꺼져 있던 동안 끊긴 서브에이전트 작업과 워크플로 실행이 있는 메인 세션이 다시 살아나면 2분(`bootGap.settleMs`) 뒤 그 목록을 담은 안내를 한 번 보냅니다(D23 `work-lost`, `boot-notice`). 재시작 뒤 하루(`bootGap.windowMs`) 안에만 보내고, 같은 중단에 두 번 보내지 않습니다. 살아 있는 omo 호스트가 없어 스스로 끝난 경우는 중단으로 치지 않습니다.
- 서브에이전트 작업과 워크플로 실행은 senpi가 쓰는 저장소에서 읽습니다. `<cwd>/.omo/senpi-task`에 기록이 있으면 그곳, 없으면 `~/.omo/agent/projects/<이름>-<sha256 12자>/senpi-task`입니다. 서브에이전트 찾기, 세션 기록 채우기(한 번 다시 실행됨), D18이 모두 이 규칙을 씁니다. 그렇게 보이게 된 오래된 기록 중 `sessions.recentMs`보다 오래된 호스트 종료·오류 기록(D8)과 한 시간보다 오래된 느린 턴(D5)은 지금의 문제로 치지 않습니다.
- 죽었거나 응답이 없는 서브에이전트, 오류로 끝났는데 아무도 처리하지 않은 서브에이전트가 있으면 부모 세션을 깨웁니다.
- 공급자 오류로 멈춘 서브에이전트 세션은 공급자가 회복되면 한 번 이어가게 합니다. 메인 세션은 알리기만 합니다(아래 "절대 하지 않는 일").
- `settings.json`을 고친 직후 공급자 설정 오류가 연달아 나고 직전까지 정상이었다면, 직전 정상본으로 되돌립니다. 거부된 파일은 `~/.omo-health/lkg/rejected/`에 보관합니다.
- 사람만 풀 수 있는 문제(모든 계정 차단, 공급자 5분 이상 불능)만 윈도우 알림으로 띄웁니다.

알리기만 하고 조치하지 않는 것도 있습니다. 캐시 폭풍, 토큰 폭증, 전체 재전송, 컨텍스트 폭주, TPS 저하, 도구 반복 루프, 오류 폭풍, 작업 폴더 밖이나 전역 설정 수정, 끝난 작업의 잔존 프로세스, 리로드 기아, 감시기 자신의 상태가 여기에 해당합니다. 토큰 폭증(D4)은 조건이 사라진 뒤에도 10분(`tokens.burnHoldMs`) 동안 같은 사건으로 유지해, 한 시간 합계가 잠깐 기준 아래로 내려갔다 올라와도 닫혔다 다시 열리지 않습니다. 리로드 기아는 보류를 일으킨 작업이 멈춘 것으로 확인된 채(작업은 실행 중인데 그 호스트가 사라짐 등) 15분(`stall.quietMs`)이 지나면 부모 세션을 깨웁니다. 죽은 서브에이전트는 이미 따로 깨우므로 다시 깨우지 않습니다. 리로드 기아는 이름이 아니라 작업 단위로 셉니다. 같은 노드 이름으로 다시 띄운 작업은 처음부터 다시 세고, 취소되거나 끝난 작업의 사건은 다시 열리지 않습니다.

## 절대 하지 않는 일

- omo/senpi 설치 파일 수정. `~/.omo`에는 스텁 한 개 외에 아무것도 쓰지 않습니다. `settings.json` 자동 복구는 예외로, 위 조건을 모두 만족할 때만 합니다.
- 분석가가 증명하지 못한 메인 세션 조치. 메인 세션은 사람이 지켜보므로 관리 대상이 아닙니다. 메인 세션의 도구 호출은 분석가가 `cause: wrong-command`(의도한 도구가 아닌 엉뚱한 프로그램이 실행됨)로 판정하고, 확신도가 `analyst.actConfidence` 이상이며, 근거(evidence)를 한 줄 이상 인용했을 때만 셸 트리를 종료하고(`release-shell`), 그 세션에 설명 메시지를 정확히 한 번 보냅니다(`followUp`, 세션이 유휴일 때만 턴을 시작). 메인 세션의 멈춤 의심(R10x, R11)은 조사 목록에 기록하지만, 이상 신호(보이는 창, 처음 보는 프로세스 계보, System32 `bash.exe` 루트, 소요 시간 이상치)가 붙은 경우에만 분석가에게 묻고, 신호가 없으면 상태 알림만 남깁니다. 분석가의 다른 판정은 알림 한 번이고 종료는 없습니다. 사용자가 자리에 있는지 여부는 어떤 판단에도 쓰지 않습니다. 그 밖의 메인 세션 프로세스 종료, 이어가기 넛지, 응답 정지 중단은 하지 않고(결정 로그에 `skipped:main-session`), 상태줄과 보고서로 알리기만 합니다. 메인 세션에 대한 보고(`report`, `/health report`)는 판정하지만, 그 결과도 그 세션에 알림으로만 갑니다. 소유자가 사라진 monitor 감시 프로세스 정리는 예외입니다. 호스트가 이미 죽은 메인 세션을 새 탭에서 다시 여는 것(D18)과 사용량 한도로 내려간 세션을 리셋 뒤 다시 띄우는 것(D20)도 예외입니다. 서브에이전트 사건을 부모 메인 세션에 전달하는 것은 이 규칙에 해당하지 않습니다.
- 이미 있는 터미널 pane에 입력하기. 크래시 재개는 omo-health가 새로 만든 탭의 셸에만 명령을 보내고, 원래 pane은 읽기만 합니다.
- 대기 중인 도구 호출, 고아 monitor 기록 또는 끝난 reflection 실행 디렉터리에 정확히 매칭되지 않은 프로세스 종료. 매칭 조건은 전체 명령, 생성 시각 창, 종료 시각 이후 유예, pid·생성시각·명령 해시 재확인입니다.
- 사용자가 띄운 셸이나 서버, 살아 있는 `tool.monitor` 루프, omo/senpi 호스트, claude.exe, Orca, 터미널 종료. 실행 셸이나 소유자 호스트가 사라진 감시 프로세스, 그리고 `final.json`이 종결된 reflection 실행만 남긴 headless 자식만 정리합니다.
- 인증 토큰 읽기. `auth.json`은 차단 필드만, `.credentials.json`은 만료 시각만 읽습니다.
- 센서의 도구 등록이나 시스템 프롬프트 수정.
- 목표 정렬 넛지로 턴을 새로 시작하거나 진행 중인 턴을 중단하는 일.

## 조사 목록과 분석가

멈춤 의심(원인 불명 R11, 오래 진행 중 R10x, 조용한 멈춤), 이상 신호, 문제 보고는 조사 목록에 올라갑니다. 감지 하나가 `~/.omo-health/investigations/<fp>.json` 파일 하나입니다. 계기(`stall`, `anomaly`, `report`, `why`), 대상, 탐지기, 분류, 증거, 신호, 상태(`open`, `analyzing`, `verdict`, `released`, `advised`, `noticed`, `closed`, `failed`), 쓴 모델, 판정, 한 조치가 들어 있습니다. 감시기만 쓰고, 대시보드와 `status`는 읽기만 합니다. `history.retentionDays`(90일)가 지난 조사는 지웁니다.

분석가는 omo를 도구 없이 한 번 실행하는 모델 호출입니다.

```text
omo -p --no-session -ne -ns -nc --no-tools --model <모델> --session-id <id> "<지시>" @jobs/<작업 id>/bundle.md
```

- 모델: omo.jsonc `"[native]".categories.<analyst.lane>.models`(기본 `deep-low`)에서 이 PC가 로그인한 공급자의 첫 모델. 없으면 `analyst.fallbackModel`. `auth.json`은 키(공급자 이름)만 읽습니다.
- 증거는 가린 묶음 파일(`bundle.md`)로만 붙이고 명령줄에 넣지 않습니다. 묶음에는 대상 세션의 최근 eval 로그(1시간 안에 쓴 것 최대 3개, 각 끝 4096바이트, `evalLogs.*`, 비밀처럼 보이는 줄은 뺌), 감지가 묻는 질문, 살아 있는 작업, 목표 정렬 기록이 들어갑니다. D15와 D21 판정은 세션마다 따로 받고 다른 세션에 다시 쓰지 않습니다. 도구, 세션 파일, 확장, 스킬, 컨텍스트 파일 없이 돌고, 이 플래그가 빠지면 실행하지 않습니다.
- 실행 파일은 `analyst.command`(기본 `omo`)이고 `OMO_HEALTH_OMO`로 바꿀 수 있습니다. 작업은 `~/.omo-health/jobs/<작업 id>/`에 남아 감시기가 다시 떠도 이어서 확인합니다.
- 답은 JSON 하나입니다: 판정(`stuck`, `progressing`, `unrecoverable`), 원인(`wrong-command`, `blocked-input`, `runaway`, `external-wait`, `unknown`), 확신도, 근거, 진단, 원리(`mechanism`: 명령이나 프로그램이 실제로 무엇을 했고 왜 막혔는지), 회피(`avoid`: 다음에 대신 할 일), 조언. `stuck`, `unrecoverable` 답에 원리나 회피가 없거나 20자보다 짧으면 쓸 수 없는 답으로 칩니다. 확신도가 `analyst.actConfidence`(0.8) 미만인 멈춤은 확인 요청으로 바뀝니다.
- 한도: 한 번 5분(`analyst.timeoutMs`), 동시에 1개(`analyst.maxConcurrent`), 감지당 2회, 시간당 8회, 하루 40회. 같은 패턴(분류 서명)에 24시간 안에 답한 원인 조사 판정이 있으면 새로 돌리지 않고 그 판정을 다시 씁니다. 보고는 따로 하루 3회입니다. 한도는 `jobs/analyst-budget.json`에 남습니다.
- 분석가가 답하지 못하면(꺼짐, 공급자 한도·장애, 3번 연속 실패로 보류, 한도 소진, 쓸 수 없는 답) 되돌릴 수 없는 조치는 하지 않습니다. 조사는 `failed`가 되고 15분(`analyst.retryMs`) 뒤 다시 묻습니다. 1시간(`analyst.holdToastMs`) 넘게 풀리지 않은 조사는 윈도우 알림으로 한 번 알립니다.

판정에 따른 조치:
- 서브에이전트: `stuck`이면 셸 트리를 조용히 종료합니다. `progressing`이면 나중에 다시 봅니다. `unrecoverable`이거나 30분 안에 두 번째 `stuck`이면 부모 세션에 `relay-cancel` 메시지를 한 번 보냅니다.
- 메인 세션: 아래 "절대 하지 않는 일"의 규칙을 따릅니다. 분석가가 엉뚱한 명령(`wrong-command`)을 증명했을 때만 셸을 풀고, 그 밖에는 알림 한 번입니다.

되돌릴 수 없는 조치에는 분석가 판정이나 구체적 증거 규칙(R5, R5b, R6, R7, R8, R9, D17 최대 보류) 중 하나가 꼭 있어야 합니다.

### 원인 조사 (0.6.0)

원인을 모르는 노란 문제는 모두 분석가가 한 번 봅니다: D1 멈춤, D8 `dead-child`·`child-error-unhandled`·`hung-main-turn`, D5 `hung-turn-child`·한 세션만의 `tps-collapse`, D10 `same-call-loop`·`error-storm`, D2 `process-runaway`. 구체적 증거 규칙(R5, R5b, R6, R7, R8, R9)으로 서브에이전트를 푼 뒤에도 한 번 봅니다. 이 조사의 계기는 `why`이고 대시보드에는 `원인 조사`로 나옵니다.

원인이 뻔한 문제는 분석가를 부르지 않습니다: 사용량 한도, 할당량, 요청 한도(429), 막히거나 취소된 계정, 설정되지 않은 공급자, 2개 이상 세션에 걸친 공급자 쪽 느림, D8 `stopped-on-errors`(같은 공급자가 다시 답한 뒤에만 뜨므로 원인은 공급자입니다).

정상이 아닌 판정이 나오면 감독 세션이 메시지를 딱 한 번 받습니다. 서브에이전트면 부모 세션, 메인 세션이면 그 세션 자신, D2 프로세스면 그 프로세스를 띄운 세션입니다. 메시지에는 무슨 일이 있었는지, 원인, 원리, 회피가 들어 있습니다. 같은 명령을 그대로 다시 돌리라는 조언은 하지 않습니다. 부모가 쉬고 있으면 이 메시지로 턴을 시작합니다. 한 감지에 한 번 보낸 뒤로는 `relay-cancel`, 알림, 원인 메시지를 다시 보내지 않습니다.

세션의 가장 높은 문제가 조사 중(`open`, `analyzing`)이면 footer가 그 문제의 수준 색으로 `👀 조사중`을 보여 줍니다. 판정이 나오면 원래 탐지기 단어로 돌아갑니다. 대시보드 조사 상세에는 진단과 조언 옆에 원리와 회피가 나옵니다.

## 기록 DB와 이상 신호

`~/.omo-health/omo-health.db`(Node 내장 sqlite)에 끝난 도구 호출의 기록(명령 유형, 소요 시간, 프로세스 계보)과 기준선 표본이 쌓입니다. `history.retentionDays`(90일)가 지난 행은 지우고, 기준선은 `history.baselineDays`(7일)만 씁니다.

이 기록을 바탕으로 기다리는 도구 호출마다 이상 신호(D19)를 봅니다.

| 신호 | 뜻 |
| --- | --- |
| `unseen-lineage` | 처음 보는 프로세스 계보 |
| `duration-outlier` | 같은 유형의 99% 분위수보다 3배 넘게 오래 걸림(표본 20개 이상) |
| `visible-window` | 보이는 창이 열림 |
| `system32-bash` | WSL 런처(System32 `bash.exe`) 실행 |

끝난 호출이 200개 쌓이기 전에는 신호를 내지 않습니다(콜드 스타트). 신호는 스스로 조치하지 않고 조사(`trigger: anomaly`)를 엽니다. 이 조사의 분석가 선택지에는 셸 종료가 없습니다. 시간당 6개(`anomaly.perHour`)까지만 엽니다. 분석가 자신의 세션은 신호와 로그 탐지에서 뺍니다. 끄려면 `{"anomaly": {"enabled": false}}`로 설정합니다.

## 목표 정렬 넛지

세션이 가장 최근 사람 요청에서 멀어지는 것 같으면 "작업 범위를 다시 확인하라"는 짧은 메시지를 보냅니다(D15). 기준은 사람이 직접 입력한 마지막 요청입니다(부모나 omo-health가 보낸 메시지, 목표 이어가기는 사람 요청이 아님). 신호는 여섯 가지입니다. 세션 나이나 도구 호출 횟수만으로는 보내지 않습니다. 오래 걸려도 할 일이 끝나고 있으면 조용합니다.

| 신호 | 조건 (기본값) |
| --- | --- |
| `churn` | 같은 파일을 90분 안에 8라운드 이상 고치며 그 사이 검사 실패가 2번 이상, 같은 검사가 90분 안에 8번 이상 실패, 또는 마지막 할 일 전환 뒤로 리뷰·검증·재작성용 서브에이전트를 4번 이상 띄움 |
| `overstep` | 마지막 사용자 말이 질문인데 파일이나 상태를 바꿈 |
| `stuck` | 같은 할 일이 진행 중인 채 20분 넘게 12단계 이상 지났고 단계 요약이 되풀이됨(고치기, 재실행, 검토), 또는 열린 할 일이 있는데 40단계 동안 끝난 할 일이 하나도 없음 |
| `reopened` | 끝낸 할 일이 다시 열림 |
| `repeat` | 거의 같은 단계 요약(숫자만 다른 것 포함)이 6번 이상 되풀이되는데 그 사이 끝난 할 일이 없음 |
| `after-complete` | 목표가 완료로 표시된 뒤에 변경을 10번 이상 함 |

`stuck`, `reopened`, `repeat`는 세션의 단계 기록에서 나옵니다. 단계는 eval의 한 줄 요약, 서브에이전트 `task_summary`, 목표 문장, 할 일 시작/완료/재시작입니다. 활동 시간은 15분 넘게 쉬지 않은 마지막 구간(`align.idleGapMs`)만 셉니다. usage limit 대기나 밤이 끼면 그 앞의 단계는 근거가 되지 않으므로, 오래 멈췄다 재개한 세션은 재개 뒤에 새로 쌓인 근거가 있어야 넛지를 받습니다. 넛지는 근거를 그대로 적습니다(예: "12 steps on 'Fix X' since 14:02Z, most repeated: ...").

세션이 유휴면 다음 턴에 붙여 전달하고(`nextTurn`), 작업 중이면 진행 중인 턴에 끼워 넣습니다(`steer`). 넛지는 턴을 새로 시작하지 않고 진행 중인 턴을 중단하지도 않습니다. 읽고 어떻게 할지는 세션이 정합니다.

0.8.0부터 넛지는 먼저 분석가에게 묻습니다(`align.requireVerdict`). 정상이라 하면 보내지 않고, 정상이 아니면 분석가 답(`Analyst: ...`)을 함께 보냅니다. 분석가가 답하지 못하면 규칙 메시지를 그대로 보냅니다. 메시지는 사람의 마지막 요청을 그 나이와 함께 인용합니다(예: "(5h ago)"). 서브에이전트 완료, monitor 알림, 워크플로 진척은 진척으로 보고 `stuck` 구간을 다시 셉니다. 리뷰·검증 에이전트의 설계된 반복과 호스트가 사라진 서브에이전트는 보지 않습니다. 횟수 한도는 실제로 전달된 넛지만 씁니다. 전달되지 못한 넛지는 매 확인이 아니라 5분 뒤 다시 시도합니다.

횟수 제한은 넛지를 받는 세션마다 45분에 한 번(`align.minGapMs`), 하루 4번(`align.perDay`)입니다. 서브에이전트의 넛지는 부모가 받으므로, 같은 부모의 서브에이전트들은 부모의 한도 하나를 함께 씁니다. 질문 여부는 문장 단위로 판단하며, 한 문장이라도 명령형(`~해`, `~줘` 등)·행동어(커밋, 푸시, 구성, 배포, 정리해)·제안(`~해야 하는 거 아닌가`)이면 질문이 아닙니다. `overstep`은 같은 요청에는 한 번만 보내고 요청 내용이 바뀌어야 다시 보내며, 다른 신호는 수치가 두 배로 커지기 전에는 24시간 안에 다시 보내지 않습니다. 끄려면 `{"align": {"enabled": false}}`로 설정합니다.

세션별 기록은 `~/.omo-health/alignment/<세션 id>.json`에 남습니다. 원래 목표, 최근 요청 10개, 열린 할 일, 보낸 넛지, 최근 단계 50개가 들어 있고 `/health`의 "원래 목표"와 `status --json`의 `alignment`가 이 파일을 읽습니다.

```json
{
  "monitorOrphans": {
    "enabled": true,
    "graceMs": 60000
```

## 파일

`~/.omo-health/` 구성:

| 경로 | 내용 |
| --- | --- |
| `config.json`, `config.last-good.json` | 설정과 마지막으로 읽을 수 있었던 사본 |
| `daemon.json` | 감시기 하트비트. `config` 필드에 반영한 설정의 수정 시각, 적용값, 거부 이유 |
| `state.json` | 사건 기록과 넛지 이력. 감시기가 다시 떠도 같은 알림을 또 보내지 않게 함 |
| `omo-health.db` | 도구 호출 기록과 기준선 표본(위 "기록 DB와 이상 신호") |
| `investigations/` | 조사 목록. 감지당 파일 하나 |
| `jobs/` | 분석가 작업(`<작업 id>/bundle.md`, 출력)과 한도 `analyst-budget.json` |
| `boot-gaps/` | 감시기 중단 기록(D23). `bootGap.keepDays`(7일) 뒤 지움 |
| `deaths/` | 감시기 죽음 기록. `history.retentionDays`가 지나면 지움. `status --json`의 `deaths`(개수, 마지막 종류와 시각) |
| `intake/` | `report`와 `/health report`의 보고 대기열. 처리한 보고는 `processed/`에 7일, 500개까지 |
| `lkg/` | `settings.json` 직전 정상본과 거부된 파일(`rejected/`) |
| `status/` | 세션별·전체 상태. 상태줄과 `/health`가 읽음. `status/_sessions.json`은 대시보드 세션 현황의 원본 |
| `sessions/ended-*.jsonl` | 끝난 세션 기록. 대시보드 세션 기록 탭이 읽음 |
| `reports/<날짜>/` | 한국어 사건 보고서 |
| `decisions/<날짜>.jsonl` | 모든 결정의 기계용 기록 |
| `alignment/<세션 id>.json` | 세션별 목표 정렬 기록 |
| `snapshots/` | 증거 스냅샷. 7일, 200개까지 |
| `inbox/` | 세션에 보낼 메시지 |
| `receipts/` | 메시지 수신 확인 |
| `logs/daemon.log` | 감시기 자체 로그 |
| `app/` | `boot.mjs`(부트스트랩), `current.json`(채널, 버전, sha, 경로), `releases/<버전>-<sha>/`(고정 설치본) |

보존: `alignment/`, `status/`, 수신 확인, 빈 `inbox/` 폴더는 7일이 지나면 저절로 지웁니다. `decisions/`, `reports/`, `snapshots/`는 이 정리에서 빠집니다(스냅샷은 위 한도만 따름).

`~/.omo-keepwarm/status/_global.json`은 omo-keepwarm이 쓰는 상태 스냅샷입니다. omo-health는 읽기만 하고, `status`와 `/health`에 한 줄로 보입니다(`staleAfter`가 지났거나 깨졌으면 `keepwarm: unknown`). 위치는 `OMO_KEEPWARM_HOME`으로 바꿀 수 있습니다.

## 알려진 한계

- in-process 서브에이전트에는 어떤 확장도 로드되지 않습니다. 그래서 서브에이전트 안에서 미리 막을 수는 없고, 밖에서 교정합니다. 서브에이전트에게 보내는 안내는 부모 세션을 거칩니다.
- process 모드 서브에이전트(`task.pid` 아래 셸)는 단위 테스트로만 검증했습니다. 현재 설정에서는 이 모드를 띄울 수 없습니다.
- 크래시한 세션을 다시 여는 것은 herdr 안에서 돈 세션만 합니다. Orca 터미널은 omo 프로세스에 터미널 핸들을 넘기지 않아(`ORCA_PI_STATUS_OWNED` pid뿐) 안전하게 고를 방법이 없으므로 알림만 띄웁니다.
- 메인 세션 모델 응답 정지는 알리기만 합니다(`abortHungTurn`은 기본값 꺼짐이고, 켜도 메인 세션 규칙 때문에 실행되지 않습니다).
- 윈도우 알림 배너는 Windows 방해 금지 설정에 따라 보이지 않을 수 있습니다. 이 경우에도 알림 센터에는 남습니다.
- 센서를 처음 설치하거나 갱신하면 각 omo 세션이 유휴일 때 한 번 핫리로드됩니다.
